# 连接与业务故障排查。

先识别失败发生在哪一层，再做用户请求范围内的最小验证。MCP 连接成功、API 查询成功和代理实际转发成功是不同结果，不能互相代替。不要主动批量调用接口、持续轮询、探测外网或消耗代理流量。

## MCP 服务是否连接。

症状包括找不到蜘蛛 IP 工具、服务启动失败、客户端只给文字建议或无法建立连接。

- 检查客户端是否支持本地 stdio MCP，以及对应服务是否启用。当前服务没有远程 MCP URL，不能把官网或业务 API 地址填为远程 MCP 地址。
- 检查客户端配置中的启动命令、参数和安装路径，以及客户端能否找到 Node.js 和所用启动程序。统一 `install` 已将运行文件放入固定目录，启动不依赖临时下载缓存；手动使用 `npx` 的首次启动可能需要下载依赖和构建。先查看相关启动错误，不因等待较久反复启动服务。
- 确认 `ZHIZHUIP_TOKEN` 通过该 MCP 服务的环境变量传入；OpenCode 使用 `environment` 字段，其他已适配客户端使用 `env`。统一安装会同时填写 API 地址和超时，并用 Node.js 直接启动固定目录中的 `dist/src/index.js`。不要假设另一个终端里的环境变量已经传给客户端。
- 查询工具存在而购买、续费等工具缺失时，检查是否启用了 `--readonly` 或客户端禁用了工具。不要自行移除只读配置；需要写操作时先说明当前能力限制。
- 用户要求验证账号接入时，可调用 `user_balance` 做一次最小查询。余额返回只证明该次 MCP 与 API 调用成功，不证明代理能够转发流量。

查看日志时只保留相关错误、时间和必要版本信息，不输出完整环境变量、API Key、确认码、账号密码或带凭证的代理 URL。向用户收集信息时要求脱敏错误，不要求发送真实 Key。

## API 认证与请求是否成功。

MCP 已连接，但工具提示缺少 Key、API Key 无效、访问频繁、超时或响应格式异常时，检查这一层。

- 缺少 `ZHIZHUIP_TOKEN` 时，检查当前服务的环境变量。需要更新统一安装的 Key 或产物时，在本机重新运行 `install`，沿用目标客户端、安装范围和只读选项，再重新加载客户端；不读取或展示 Key 原文来证明配置。
- API Key 无效或已删除时，让用户在网站 API Keys 页面核对有效性和复制完整性，必要时重新生成，并按原接入方式更新服务环境变量或重新运行统一安装。各客户端分别保存 Key，需要更新的客户端都应包含在本次选择中。API Key 与代理账密、主账号切换 token 是不同凭证，不能互换。
- 访问频繁时停止密集调用，遵循返回提示后再按需查询；不要并发放大请求或循环重试。查询“全部”时按分页完成并报告覆盖范围。
- 请求超时、网络失败或响应格式异常时，记录受影响的工具和脱敏错误。先区分只读查询与写操作；写操作不能根据错误就断言后端未执行。

`main_account_switch_token` 是获取动态住宅主账号的切换 token，并不是执行 IP 切换。它当前被 MCP 标为只读，但后端没有 token 时可能生成并保存一个；不要为了健康检查调用它，也不要据此承诺只读模式绝对不会改变任何数据。

## 业务条件是否满足。

API 能响应，但返回余额不足、验证未完成、参数不支持、账号不可续费、库存不足或退单审核中时，按具体业务原因处理。

- 根据当前工具 schema 核对产品、必填参数、期限、数量、单位和 ID 来源。未知字段不要反复试填，不绕过 MCP 直调后端。
- 动态带宽后续操作使用 `rows[].sub_account`，其他产品按工具说明使用账号 ID；所有此类编号按字符串传递。不要把本地记录 ID、代理用户名和业务账号编号混用。
- 账号不支持某操作时，核对产品适用范围及返回状态。动态带宽的 `can_renew`、`can_upgrade`、`refunding` 可帮助判断当前操作资格，不因名称相似套用其他产品工具。
- 余额、实名或联系方式验证不足时，说明网站上的必要处理步骤。不要代用户充值、绕过验证，或擅自调整购买方案。
- 当前 MCP 没有动态带宽的专用报价或订单详情工具，费用和订单状态需要在网站核实。
- 写操作“待确认”表示尚未执行；确认码静默期结束不等于用户授权。等待用户真实同意后再继续，拒绝或取消则停止。
- 退单申请成功只表示提交审核；审核中不重复提交。扣费操作结果未知时，先核对现有记录，不能直接重新购买、续费或升级。
- 子账号删除可能返回 `code=1` 且 `msg` 提示未找到或删除失败；批量限流可能整体成功但包含失败数量。必须读消息与明细，必要时查询目标复核；失败的限流设置甚至可能移除原限制，详见[子账号管理](account-lifecycle.md)。
- 动态备注或限流修改后出现连接行为变化时，核对后端默认配置副作用；不要先反复改密、换协议或重新提交同一修改。

## 代理是否实际连通。

API 查询正常但业务程序无法使用代理时，才进入代理连接排查。`sub_account_list` 提供已有子账号的信息，不是独立的 IP 提取或连通性测试工具。

1. 核对用户指定账号的产品、有效期、可用流量或带宽、禁用状态，以及接口实际返回的入口、端口和协议。`target` 是代理入口相关字段，`ip` 可能表示出口 IP；不要直接互换。字段为空时报告缺失，不猜测补齐。
2. 核对代理用户名和密码是否使用正确位置，并区分 API Key、代理账密和连接串附加参数。展示示例时使用占位符；只有用户明确需要实际连接配置时，才在其指定交付位置使用必要凭证，不写入日志或公开文档。
3. 动态住宅流量的会话参数参考 MCP 资源 `zhizhuip://docs/dynamic-proxy-session`。不要把创建会话等同于创建业务子账号，也不承诺不同会话一定获得不同出口 IP，或指定时长内绝不切换。其他产品是否支持相同参数，以其说明为准。
4. 只有用户明确要求验证真实代理连通性时，才对其指定或确认的目标进行最小次数测试，并说明可能消耗流量。不扩大目标范围，不做压测、持续轮询或批量网络探测。
5. 报告实测边界：测试了哪个账号、哪种协议、哪个目标，以及连接或转发在哪一步成功或失败。一次成功不代表全部目标可访问，也不代表持续稳定。

不要为了排查擅自更换代理账密、开关端口、修改白名单、删除账号或购买新资源。诊断发现需要这些操作时，先说明目标与影响，再进入对应写操作流程。
